# Test guard profile (E5 part 2)

Generated by `node eval/e5/profile-guard.js --report` from the raw files in `eval/results/E5/guard-profile/` (one JSON per run). Each run is a scratch clone of this repo at a real commit's parent with that commit's changes staged (everything but `.proof/`), and `pocp fix` run on it in-process, exactly as an agent would. POCP's process runner is wrapped to timestamp each check run; the log name POCP gives each run says what it was. Nothing in POCP is changed by the wrapper.

Machine: Apple M1 Pro, 8 CPUs, darwin 24.6.0, Node v22.13.1. Scenarios: `ca3e9f6`, `df0305b` (each edits `test/e2e-guard-mechanical.test.js`; required checks `unit-tests`, `engine-tests`, `test-suite` = `npm test`, 10 mutants, seed 1).

**Machine load.** The Mac was shared with other agents' work throughout (1-minute load average, sampled every 10 s, in each table). On 8 CPUs, a load of 40+ means every check ran several times slower than it would alone; the absolute times below are this machine under this load, not POCP's speed. The *shares* and *counts* are what carry over.

## What this shows

From the 5 completed runs of the previous guard (`ca3e9f6`, `ca3e9f6`, `ca3e9f6`, `ca3e9f6`, `df0305b`):

- **The guard is almost all check runs.** Snapshots, copies, restoring old tests and building the mutation plan take about a second in total (setup gaps below; a tree snapshot is 0.2 s, a copy 0.1 s). Reusing snapshots or caching plans can't matter.
- **The old-tests baseline ran alone:** 32%, 40%, 41%, 37%, 19% of guard wall time, one check at a time, with the other job slots idle. The new-code baseline was already reused from the plain proofs in every run.
- **The full suite dominates the mutant phase:** 76%, 72%, 76%, 67%, 71% of mutant check-seconds. Mutants that reached it on the old side: 4 of 10, 4 of 10, 4 of 10, 4 of 10, 7 of 10. Every mutant the old tests miss runs all three checks; every one only the suite catches runs all three on the old side and, before this change, all three again on the new side.
- **Overlap:** the suite (`node --test test/*.test.js`) contains the unit and engine test files, so those ran twice in each copy that reached it: 653.8 s, 818.5 s, 639.9 s, 1024.1 s, 1951.7 s of check time. Skipping the faster checks when the suite will run anyway would be safe only if the suite provably runs a superset of their tests, which POCP can't know from two shell commands; not done.
- **Parallelism:** 8 CPUs; the guard runs up to 4 mutant checks at once (min(4, CPUs − 1)), and achieved 3.0, 3.2, 3.1, 3.0, 2.7 on average in the mutant phase. The phase ends with one or two slow mutants (caught only by the suite) running alone, so more jobs would not shorten it; `node --test` already runs test files in parallel inside each check.
- **Load can change mutant outcomes.** 3 run(s) had checks hit the 10-minute check timeout (`after-paired-ca3e9f6-1-2026-10-28T23-52-46-331Z`: plain test-suite, guard-new test-suite; `before-df0305b-1-2026-10-28T23-23-58-623Z`: m3 new test-suite, m1 new test-suite, m7 old test-suite, m8 old test-suite, m7 new test-suite, m8 new test-suite; `before-paired-ca3e9f6-1-2026-10-28T23-52-37-644Z`: plain test-suite, guard-new test-suite). The guard counts a mutant whose check times out as caught, so on a loaded machine a mutant the suite would miss can count as caught on the old side (raising the bar the new tests must meet), and a timed-out baseline makes the verdict inconclusive. Those runs are excluded from the before/after medians; the later rounds raised the scratch clone's timeout to 60 minutes (committed on top of the parent, so the base has it too).
- **The critical path** is the slowest mutant: unit → engine → suite on the old side, then, before this change, unit → engine → suite again on the new side. Killer-first cuts that second chain to the suite alone.

## Speedups considered

The rule: a change ships only if every verdict and every mutant outcome stays identical for the same inputs (same mutants sampled with the same seed, same caught/missed on each side, same verdict). `test/e2e-guard-equivalence.test.js` runs a frozen copy of the previous guard (`test/guard-v0/`) and the new one on fixtures that reach every verdict (passed, detection-dropped, behavior-changed, baseline-red, inconclusive), with several seeds, mutant budgets and job counts, and requires the full result objects to be equal once durations are removed. The fixtures include mutants caught only by a slower check, so the new schedule is exercised, and two more tests check that it is (killer-first order; mutants running during the baseline within the job limit and stopping at its first failure). The paired runs above compare the real result objects too.

| Candidate | Done? | Why |
|---|---|---|
| Start mutants alongside the old-tests baseline, sharing the job limit | **yes** | The baseline ran one check at a time for a third or more of the guard. Mutant results are used only if both baselines pass; from the first old-tests failure every mutant stops before its next check and is discarded. Check order now comes from the new-code baseline's (or the reused plain proofs') durations instead of the old-tests baseline's; the previous guard already ordered by measured durations, which vary run to run, so it already relied on a check's result not depending on which checks ran before it in the same copy. |
| Killer-first on the new side | **yes** | A mutant is caught if any check fails, so running first the check that caught it on the old side changes only how soon that is known. On the slowest mutant it removes a unit + engine run from the critical path. Same assumption as above. |
| Fastest-first order on the old side | kept | Unit tests cost seconds and caught 6 of the 7 caught mutants in `ca3e9f6`; putting a slower check first would cost minutes on those. |
| Skip a check whose tests the suite also runs | no | Not provable from two shell commands; the task rules it out unless provable. It is the largest remaining overlap (see above). |
| Reuse snapshots / cache the plan | no | Setup is about a second of a 20+ minute guard. |
| Cache check results by code hash | no | Within one guard every mutant tree is different, the new-code baseline is already reused from the plain proofs, and whole guard results are already cached by subject. |
| Avoid redundant base runs | no | The base run happens only when the old tests fail on the new code, and only for the checks that failed; nothing to cut. |
| More jobs | no | The tail is one or two slow mutants running alone; extra slots would sit idle. Under outside load it would also raise the chance of the timeouts above. |
| Speculatively start a caught-looking mutant's new side before its old side finishes | not tried | Would shorten the critical path further using idle slots at the tail, with results discarded when the old side misses. More moving parts; left as a candidate. |
